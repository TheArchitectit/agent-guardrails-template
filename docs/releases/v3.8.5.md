# Release Notes — v3.8.5

**Release Date:** November 12, 2026
**Type:** Patch (CI gate fix)

## What shipped

- **`Release Coverage` can see merge commits.** Its reports-only exemption
  listed changed files with `git diff-tree --no-commit-id --name-only -r HEAD`.
  That command returns **nothing** for a merge commit without `-m`, so a merge
  that brought only `docs/qa/fleet-sweeps/*` and `docs/qa/spec-sweeps/*` never
  reached the exemption and fell through to
  `::error::HEAD <merge> is not release <tag> (<release commit>)`.
  The exemption now diffs against `HEAD^1` — where `main` was — which is the
  right question on a merge ("what did this push add to `main`?") and
  identical to the old command on an ordinary commit.

## Validation

The defect and the fix were both run against real history rather than
asserted. Running the step's own commands under bash at the incident commits:

| Commit | Old | New |
|---|---|---|
| `af0f102` (the merge) | `FALLTHROUGH (changed=0)` → fail | `SKIPPED (not a product release)` |
| `6a9d7d0` (the release) | not reports-only → HEAD-must-be-the-tag | same |
| `050b8a0` / `34f85b8` (sweeps) | `SKIPPED` | `SKIPPED` |

So the merge blind spot closes and the two behaviours the gate exists for are
unchanged: a product push still requires HEAD to be the annotated release,
and a generated-report-only push is still skipped. The YAML parses. The
regression gate and the guardrails scan run over this tree before the tag is
created. `Release Coverage` requires HEAD itself to be the annotated `v3.8.5`
tag named by `VERSION`, with a `## [3.8.5]` changelog heading — which is why
the version artifacts are updated in the tagged commit, not in a later one.

## Deliberate boundaries

No product code, policy pack, or spec behavior changes. The change is one
command in `.github/workflows/release-coverage.yml`. The AIGGP/DevGate copy
carried the identical command and is fixed there in `v1.3.18`, from the same
observation (`af0f102`, 2026-11-12, when `deploy.sh`'s push was rejected by
concurrent automated sweep writers and the release had to land as a merge).

One consequence is recorded rather than resolved here: a merge that brought
only generated reports is now correctly skipped even when the merge's *second*
parent is the release. A merge whose first parent is not the release will
still fall through to HEAD-must-be-the-tag and fail, which is the intended
shape — that `main` moved to something that is not the tagged product state.

## Version ancestry

This release sits directly on `v3.8.4`. `VERSION`, `CHANGELOG.md`, the release
notes, the releases index, and the README are updated in the tagged commit
itself.
