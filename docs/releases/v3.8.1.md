# Release Notes — v3.8.1

**Release Date:** November 5, 2026
**Type:** Patch (release automation repair)

## What shipped

- **The release pair can schedule again.** `Release Published` and
  `Release Coverage` declared `runs-on: devgate`. This repository registers one
  self-hosted runner, `ucs03-guardrails` (label `guardrails-ucs03`), so no job
  carrying the `devgate` label could ever be assigned. Both runs sat queued from
  2026-11-05T03:43:51Z while the six sibling workflows in the same push finished
  on `ubuntu-latest` and `guardrails-ucs03`.
- **v3.8.0 never got its GitHub Release.** Because the publisher could not
  schedule, the tag, `VERSION`, and changelog existed but the GitHub Release
  object did not. README asserted it was there. That gap is repaired here.

## Why `ubuntu-latest` and not the UCS03 runner

Routing the publisher to `guardrails-ucs03` would have been the obvious repair
and is forbidden by Spec 19 R19-13: the self-hosted label may appear in exactly
one file (`team-validation-fleet.yml`), that job is `main`-only, and it must
carry no write scope. Publishing a release needs `contents: write`. GitHub-hosted
runners are inside the allowed prefix set, so both jobs go to `ubuntu-latest`
without widening the trusted surface.

## Validation

`scripts/check_runner_isolation.py` over the edited tree reports
`R19-13 OK: 8 workflow(s), 5 pull_request workflow(s) on hosted runners,
1 self-hosted job in .github/workflows/team-validation-fleet.yml`. The failing
state was the unschedulable pair itself; the passing state is Release Coverage
executing on this push and Release Published creating the tag's release.

## Deliberate boundaries

This release changes no product code and no guardrail behavior. It changes
which runner executes two release workflows. The v3.8.0 release object is
published from its existing annotated tag rather than by moving that tag.
