# Release Notes — v3.5.0

**Release Date:** August 18, 2026
**Branch:** `main`
**Type:** Minor version bump (new feature — pi extension bash permission UX)

---

## Highlights

🔓 **Interactive bash permission prompts** — Bash commands in the pi extension are no longer hard-blocked. Dangerous commands now prompt for approval with four scopes: *Allow once*, *Allow for session*, *Always allow*, and *Deny*. Safe commands at the `ask` level get the same prompt instead of a dead-end block message.

🛡 **Catastrophic-tier type-back** — The most dangerous commands (`rm -rf /`, `mkfs`, fork bombs, `dd of=/dev/…`) are still grantable — never a hard block — but require typing the command back verbatim before the scope prompt appears. A safeguard, not a ceiling.

📋 **Persisted danger allow-list** — A new `guardrail_allow_danger` tool manages a persisted allow-list at runtime: add exact commands or regex patterns, remove, list, or clear. Allow-listed commands skip the prompt entirely. Stored in `~/.pi/agent/extensions/pi-guardrails/allowlist.json`.

⚙️ **Legacy mode toggle** — Teams that want the old hard-block behavior can set `allowDanger.enabled: false` in config.json. The default is `true` (interactive prompts).

📊 **Full audit trail** — Every allow, deny, and allow-list mutation is logged to `violations.jsonl` with severity: `info` for allows, `warning` for denies, `critical` for `clear` and legacy dangerous-blocks.

## What's New

### Unified bash permission handler

A single handler, `createBashPermissionHandler`, now owns the full bash decision path. It replaces both the old `createBashSafetyHandler` (hard-block on dangerous patterns) and the bash branch of `createPermissionHandler` (which treated `ask` as a block with no prompt).

**Decision flow:**

```
bash tool_call
  ├─ normalize(cmd)                     # trim + collapse whitespace
  ├─ allowDanger.enabled === false?  ──→ legacy deny behavior (block dangerous, ask blocks)
  ├─ allow-list match(cmd)?          ──→ allow (audit: allowlisted, entry info)
  ├─ classify(cmd) → category         # "safe" | dangerous tier category
  ├─ safe + level "auto"             ──→ allow
  ├─ safe + level "blocked"          ──→ block
  ├─ safe + level "ask"              ──→ simple prompt (scope choices)
  ├─ dangerous + level "blocked"     ──→ block (audited)
  └─ dangerous                       ──→ strong prompt
        └─ catastrophic tier?        ──→ type-back confirmation prompt
  prompt resolves to:
    ├─ deny      ──→ { block: true } + audit denied
    ├─ once      ──→ allow this call only (no state written)
    ├─ session   ──→ allow + record in session allow set (cleared on restart)
    └─ always    ──→ allow + persist exact command to allow-list file
```

**Scope choices** (presented via `ctx.ui.select`):

| Choice | Effect |
|--------|--------|
| Allow once | Allows this call only — no state written |
| Allow for session | Allows this command for the rest of the session (in-memory) |
| Always allow | Persists the exact command to the allow-list file |
| Deny (or dismiss) | Blocks the call |

**Non-interactive contexts** (no UI available, e.g. RPC/print mode): bash that would prompt is denied with an audited reason. This preserves today's observable behavior for non-interactive runs.

### Catastrophic tier

Four command classes get a stronger prompt — type-back confirmation — before the scope choices appear. They are still fully grantable; the type-back is a UX safeguard, not a hard block.

| Pattern | Example |
|---------|---------|
| Fork bomb | `:(){ :\|:& };:` |
| `mkfs` as a command token | `mkfs.ext4 /dev/sdb1`, `sudo /sbin/mkfs /dev/sda` |
| `rm` with flags targeting bare `/` | `rm -rf /`, `rm -fr /*`, `rm -rf --no-preserve-root /` |
| `dd` writing to a device node | `dd if=/dev/zero of=/dev/sda` |

The `mkfs` pattern requires `mkfs` to appear as a command token (optionally path-prefixed) with a known filesystem-type suffix or end-of-token — so benign strings like `cat mkfs.txt` or `less my-mkfs-file` are not flagged. The `rm` pattern allows any sequence of flags between `rm` and the bare root path, so `--no-preserve-root` is caught.

Set `allowDanger.requireTypebackForCatastrophic: false` in config.json to degrade the catastrophic tier to the standard strong prompt (no type-back).

### `guardrail_allow_danger` tool

A new pi extension tool for runtime allow-list management:

| Action | Params | Behavior |
|--------|--------|----------|
| `add` | `command` (exact) or `pattern` (regex); `reason` (required for pattern); `sessionOnly?` | `sessionOnly` records in the session set only (exact only); otherwise persists to allow-list. Audited. |
| `remove` | `command` or `pattern` | Removes the matching entry. Audited. |
| `list` | — | Returns all entries with type/reason/source/addedAt |
| `clear` | — | Empties the allow-list. Audited as a critical violation-log entry. |

Validation: providing both `command` and `pattern` returns an error (on `add` and `remove`). `sessionOnly` with `pattern` returns an error. Invalid regex is rejected, never thrown.

### Configuration

New `allowDanger` section in `~/.pi/agent/extensions/pi-guardrails/config.json`:

```json
{
  "allowDanger": {
    "enabled": true,
    "requireTypebackForCatastrophic": true
  }
}
```

- `enabled: false` → bash reverts to legacy hard-block behavior (dangerous blocked, `ask` blocks with chat-instruction message).
- `requireTypebackForCatastrophic: false` → catastrophic tier degrades to the strong prompt without type-back.

Partial `allowDanger` objects merge with the defaults — a config with only `{ "requireTypebackForCatastrophic": false }` still enables the feature.

### Storage

A new file joins the extension storage directory (`~/.pi/agent/extensions/pi-guardrails/`):

- `allowlist.json` — persisted dangerous-command allow-list (exact entries and regex patterns, with source/reason/addedAt).

Corrupt or unreadable allow-list files are tolerated: the list starts empty, a warning is logged, and the next write recreates the file. Invalid regex in a persisted pattern entry is skipped at load with a `console.warn`.

### Audit

All bash decisions append to `violations.jsonl` via `ViolationLog.log`:

| Decision | Severity |
|----------|----------|
| Allow via allow-list | `info` (details include entry type + source) |
| Allow via session allowance | `info` |
| Allow via prompt (once/session/always) | `info` (details include chosen scope) |
| Deny via prompt (Deny or dismissed dialog) | `warning` |
| Deny — no UI available | `warning` |
| Deny — catastrophic type-back mismatch | `warning` |
| Deny — prompt failure (UI threw) | `warning` |
| Block — `blocked` permission level (safe or dangerous) | `warning` |
| Block — legacy mode dangerous command | `critical` |
| Allow-list `clear` via tool | `critical` |

## Migrating from v3.4.x

### For users who relied on the hard-block

The default behavior changes: bash commands that were previously hard-blocked now prompt for approval. If your workflow depended on the block (e.g. a non-interactive pipeline that treated the block as a signal), either:

1. **Set `allowDanger.enabled: false`** in config.json to restore the exact legacy behavior (dangerous commands blocked, `ask`-level bash blocked with the chat-instruction message), or
2. **Set `tools.bash: "blocked"`** in `toolPermissions` to block all bash regardless of danger classification, or
3. **Run non-interactively** — when no UI is available, bash that would prompt is denied with an audited reason, preserving the observable block behavior for RPC/print mode.

### For non-interactive / RPC users

No action needed. When `ctx.hasUI` is false, any bash command that would require a prompt is denied with reason `"Interactive confirmation required but no UI available; bash denied in non-interactive mode."` — audited at `warning` severity. Safe commands at level `auto` still execute without prompting.

### Config file

The new `allowDanger` section is optional. If absent, the defaults (`enabled: true`, `requireTypebackForCatastrophic: true`) apply. No existing config keys were removed or renamed.

## Known Follow-ups (non-blocking)

These were identified during review and tracked as future work, not blockers for this release:

- **Tool-level test for `guardrail_allow_danger`** — the `execute` closure captures module scope, making it awkward to test without mocking the full `ExtensionAPI`. The underlying `DangerAllowList` is fully tested; the tool wrapper's param-validation logic is not.
- **Unused `ApprovalScope` type** — exported from `types.ts` but the handler uses string-literal switch cases instead. Dead code, harmless.
- **`echo mkfs` triggers catastrophic type-back** — false positive on the safe side (the command is already caught as dangerous by the destructive pattern). Tightening further risks regressing the `sudo /sbin/mkfs.ext4` case.
- **Fallback path category for `sudo`** — the hardcoded-fallback path in `checkCommand` reports `"destructive"` for sudo, whereas the classify engine reports `"elevated"`. Inconsistent tier mapping between the two code paths.
- **`dd of=/dev/sda` without `if=`** — not flagged as catastrophic (only the `if=`-present form is caught by the device-node pattern).
